# Agent Note：SDK cohort 0.1.2-rc.1

Status: implemented

## Problem

本仓库全家桶跟随官方 `@deepseek-ai` SDK cohort；自 2026-09-02 起停在 `0.1.2-alpha.4`，而 npm `next` 渠道已走到 `0.1.2-rc.1`（2026-09-03T06:21Z 发布，alpha.5 之后的 API 冻结候选）。继续留在冻结之前的 alpha 线，意味着下一个宿主版本发布时家族将面对无法编译的面，桌面应用的内置运行时也会 pin 在冻结前的宿主上。本次升级必须在同一改动里搬齐所有 cohort 面，并写清家族现在要求哪个宿主版本。

## Decision

全仓库一步到位迁到 `0.1.2-rc.1` cohort（提交 `9958edbf` + `04c69e85`，已 rebase 到 desktop-launcher 移除之上）：

- **依赖区间**：所有引用 `0.1.2-alpha.4` 的 `@deepseek-ai/*` 区间换成 rc.1 等价形式；精确 pin 保持精确（`shared` 的 client-ui-settings/slots、`desktop/runtime/host` → `@deepseek-ai/dsh@0.1.2-rc.1`）。`@deepseek-ai/cordis` 维持 `^4.0.2`、cosmokit `1.8.3`、schemastery `3.18.2`（support pin 不动）。
- **宿主下限，一份契约四个面**：每个家族包加 `scripts/plugin-template` 的 `dsh.engines.dsh >=0.1.2-rc.1`、`README.md`/`README.en.md` 的静态 `DSH >=0.1.2-rc.1` 徽章、`ci.yml`/`release.yml` 的 `npm install -g @deepseek-ai/dsh@0.1.2-rc.1` 挂载 pin、`docs/publish-prep.md` 的 smoke 句子。下限必须写本次安装的 cohort。
- **发布年龄策略**：rc.1 安装时还在 pnpm 11 的冷却窗口内，`minimumReleaseAgeExclude` 把 alpha.4 精确条目整体换成同集合的 rc.1 精确条目（后续上游发布拿不到旁路）。desktop runtime host 额外用 `overrides:` 块（23 条）钉住它解析到的 rc.1 面：pnpm 11.9 的门禁即便在 exclude 列表补齐后仍把那 23 个包压回 `0.1.2-alpha.4`，而全新 `npm install @deepseek-ai/dsh@0.1.2-rc.1` 探针 prefix 证明官方闭包是纯 rc.1——overrides 让桌面载荷对齐官方闭包而不是门禁的回退。其 exclude 列表记录两波（191 自动 + 23 手工）。
- **面变化证据**：对闭包内全部 44 个 `@deepseek-ai` 包做 alpha.4 树与 rc.1 树的声明级对比：零符号移除、零 exports-map 变化、零新增；工作区 typecheck 无需任何源码适配即通过。对本仓库消费的每个面而言，rc.1 是纯稳定化发布。
- **上线顺序**：宿主 CLI 必须先升到 rc.1，live `web` profile 才能对本树重启；engines 下限点名了旧 CLI 无法满足的宿主版本，且 link profile 从本检出的 `node_modules` 解析 SDK peer。

## Testing

`pnpm typecheck`、`pnpm build`、`pnpm test`（含真实宿主 boot 的 shell-isolation）、`pnpm test:scripts`（家族 engines 不变量）、`aggregate:check`、`sync-shared:check`、`runtime-deps:check`、`docs:check`、`i18n:check`、`skin-center:check`、`community:check` 在 rebase 后分支全部通过；两份 lockfile 均通过 `pnpm install --frozen-lockfile --ignore-scripts`。worktree 构建的聚合包在 rc.1 宿主二进制下挂入 scratch profile 并通过 `scripts/e2e-mount.sh` 无头渲染（better-sidebar 在场、被排除的 archive-manager 缺席）。升级前 `profile-cohort-check.sh` 报告各 profile 全部 symlink 指向宿主（无 shadow-copy 错位）。

## Alternatives considered

- **留在 alpha.4 / 跳 alpha.5**：用户指定 rc.1；alpha 线虽继续到 alpha.5，冻结版才是发布目标。
- **跳过 desktop runtime pin**（内置宿主留在 alpha.4）：会让桌面载荷的宿主代际与仓库 cohort 分叉——正是 cohort 纪律要防的模块实例分裂。
- **rebase 时手改 lockfile**：desktop-launcher 移除提交已重生成根 lockfile，冲突文件先取 dev 版，再用 `pnpm install` 对 rebase 后 manifests 全量重生成并冻结证明——从不手编。

## Consequences

- 家族现在要求 `>=0.1.2-rc.1` 宿主；旧 CLI 安装本树会按设计在 engines 下限失败。live profile 只在 CLI 升级与 `dsh web` 重启之后切换（用户侧；共享检出的 `pnpm install` + `pnpm build` 也等那次重启，避免运行中的 alpha.4 宿主吃到不一致的 bundle）。
- desktop 运行时载荷 staging（`desktop/resources/runtime/`，git 忽略）仍是 alpha.4 构建，直到有人在 `desktop/` 跑 `npm run prepare-runtime`。
- 下一次 cohort 升级重复同样的机械动作；desktop host 工程现在同时携带 exclude 台账与 overrides 块，二者必须一起搬。
