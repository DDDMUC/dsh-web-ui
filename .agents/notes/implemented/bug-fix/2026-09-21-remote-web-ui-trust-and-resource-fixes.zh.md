# Agent Note: remote-web-ui 信任与资源修复

Status: implemented

## Problem

对 `packages/dsh-remote-web-ui` 的一次只读审计（host 信任/凭据面、host 运行时、浏览器半区、客户端/服务端契约）加上针对线上处理函数的实测，发现了有具体代价的缺陷：

1. `requirePairingForLan: false` 时，`/remote` 前缀会代理每个请求到回环，并附上进程自己的 `dsh-auth-*` 凭据——即以机器所有者身份授权的凭据。任何能触达端口（局域网绑定、快速隧道、中继）的客户端都能在未配对的情况下驱动完整 host API，而配置文案只承诺桌面继续走裸 `/api`。
2. accept 限流对回环来源的请求以 `X-Forwarded-For` 的**第一个** hop 作为键——而该值由客户端控制（边缘是追加而非替换）——因此轮换该请求头即可为每个请求铸造新的爆破预算。该表也没有硬上限，同样的轮换会让它无界增长。用轮换键在线上处理函数实测：前 2 000 个请求平均 0.067 ms/请求，30 000 个请求中最后 2 000 个为 0.152 ms（2.3 倍，单调上升）；RSS +41..44 MB。
3. 竖屏适配层把每个被压制的会话/项目行记录在一个仅在 revert 时清空的 `Map` 里。React 会重建行节点，因此脱离文档的子树在页面生命周期内始终可达；带强制 GC 的 WeakRef 探针确认了这种保留。
4. 更小的已确认缺口：面板会在 `revoke`/`stop` 被拒时乐观地移除设备行（并把「停止」翻到已停止阶段），而服务端会话仍然存活，且服务对「什么都没改变」的请求不发状态变更，因此这种虚假保证可能一直保留；设备凭据被只写不读地复制进 `localStorage`（无人读取、无过期）；`publicBaseUrl` 末尾斜杠会铸造无法路由的 `//pair-accept` 链接；`/pair-app` 应用壳拉取从不丢弃过期内部凭据（重启前所有配对都 502）；心跳会对永久 401/403 无限轮询；win32 更新超时路径上的 `taskkill` 未挂 `error` 监听；浏览器回环判定缺少 host 侧已接受的方括号 `[::1]` 写法；`isTrustedHost` 遇到畸形可信主机项会抛错；以及文档与实现语义矛盾（「一次性」令牌在其窗口内可重复配对；空闲默认值写成 7 天而实际为 30 天）。

## Decision

- **进程内部浏览器认证凭据只随「已出示有效配对设备凭据」的请求发送。** `/remote` 的 HTTP 与 WebSocket 处理都先解析设备凭据，只有其有效时才传入 `deps.auth`。关闭 `requirePairingForLan` 时通道仍会代理过期同源改写（不返回 403），但未配对的调用会被转发而不带该凭据，内层路由返回 401。配置 JSDoc 与中英 README 安全模型均已说明。
- **accept 限流只信任边缘追加的 XFF hop，并有硬上限。** `rateLimitAccept` 取请求头的**最后一个** hop（边缘追加它看到的地址；更早的 hop 由客户端提供），`acceptLimitKey` 将其截断到 64 字符。桶表由 `MAX_ACCEPT_BUCKETS`（1024）限制并按 FIFO 驱逐；过期改为摊销：从按插入序排列的表头开始清理，因为重新起窗的桶会重新插入到表尾，所以每请求 O(1)。
- **适配层会遗忘 React 已脱离文档的行。** `disableRowDrag` 对任何已不再连接但仍在跟踪中的行写回记录的 `draggable` 状态并删除该条目，因此表内只保留存活行；`restoreRowDragState` 与 revert 路径共用。
- **公网地址在进入服务时规范化为其 origin**（`PairingService.setPublicBaseUrl` 经 `canonicalBaseUrl`），末尾斜杠或路径因此不会铸造无法路由的 `//pair-accept` 链接。
- **设备凭据仅限会话作用域。** `/pair-app` 捕获脚本只写入 `sessionStorage`；从不被读取的 `localStorage` 副本已删除。
- **被拒的撤销或停止不会改动面板名单。** `RemoteEntry` 只在请求成功后应用乐观的阶段/名单变更，因此 403 或网络失败会保留服务端权威的设备行，而不是声称一次并未发生的撤销。
- **当服务器证明永远不会接受该页面时停止轮询。** `sendHeartbeat` 返回响应状态，`shouldStopHeartbeat`（401/403）清除 10 秒定时器；瞬时错误保持原节奏。
- **其他正确性修复**：应用壳拉取在 401/403 时丢弃过期内部凭据；win32 `taskkill` 子进程挂上 `error` 监听；浏览器回环判定（及引导脚本守卫）接受 `[::1]`；`isTrustedHost` 忽略无法解析的可信主机项而不是抛错；删除只写不读的 `consumed` 令牌标志，并把自相矛盾的 `accept()` 注释改为「窗口内始终可作凭据」的语义；空闲默认值文档改为 30 天。

## Alternatives considered

- **恢复真正的一次性令牌**（让 `accept()` 返回既有的 `used` 码并回 409）。否决：窗口内可重复配对是为跨 cookie 上下文的移动流程（相机预览 → 应用内浏览器 → 系统浏览器）刻意做的让步，且测试已固定该行为。错误在于文案与代码注释，因此改为修正它们；`used` 作为旧版或第三方 host 仍可能返回的分支保留在 wire 契约中。
- **继续以第一个 XFF hop 作为限流键**，依赖令牌熵。否决：限流是配对端点唯一的未认证洪水约束，键由调用方控制会让它形同虚设，同时仍然消耗内存。
- **关闭策略时仍要求 `/remote` 配对**（回 403 而非 401）。否决：关闭策略模式的既定用途就是让过期的同源改写继续可用，403 会直接破坏它；不发放凭据既保留既定行为，又消除了机器所有者访问。
- **缓存应用帧并把适配 tick 的查询根植于它**（每 600 ms tick 的 7 次全文档扫描中的 5 次）。本轮未实现：收益真实，但选择器语义变化需要在真实 GUI 上做一轮浏览器 QA，且 tick 已由折叠观察者驱动收敛。留待后续。
- **端到端删除 `used` wire 代码。** 暂不采纳：客户端映射与其文案是「host 确实回 409」时的优雅路径；在没有对应故障需要修复的情况下删除它属于 wire 契约变更。

## Consequences

- 关闭配对策略的运维者不再获得静默的机器所有者旁路，但此类部署上过期的客户端改写现在会看到 harness 的 401，而不是可用的代理。这正是文档化的「裸 `/api`」模型，并已在安全模型中说明。
- 在持续的轮换键洪水下，限流可能驱逐合法桶并重置该客户端的窗口。无论何种情况，令牌猜测都不可行（128 位令牌）；该上限换来的是有界内存与平坦的每请求成本。
- 脱离文档的行会保留其官方 `draggable` 状态直到下一个 600 ms tick，而不是直到 revert；该 tick 在适配层激活期间本就在运行。
- 撤销后心跳不再刷新在线状态，因此被撤销的手机会立即不再计入在线，而不是每 10 秒一次。

## Testing

- `tests/remote-api.spec.ts`：关闭策略时，未配对请求不带（也从不兑换）进程凭据；有效配对设备仍会带上。
- `tests/routes.spec.ts`：轮换的前置 XFF hop 因最后一个 hop 而落入同一限流窗口；末尾斜杠公网地址铸造可路由的二维码 URL；畸形可信主机项被忽略。
- `tests/pair-api.spec.ts`：心跳状态被回传，停止判定仅限 401/403。
- `tests/remote-entry.spec.tsx`：被拒的取消配对会保留设备行（该测试在修复前的乐观变更下失败）。
- `tests/mobile-adapt.spec.ts`：脱离文档的行不再被跟踪；该 spec 会清理新模块实例启动的定时器，避免陈旧适配层跨用例干扰。
- 实测（同一脚本、30 000 个轮换键、每版本三次）：基线 0.067 ms 升至 0.152 ms/请求，RSS +41..44 MB；修复后 0.059 ms 降至 0.041 ms，无增长趋势。RSS 差值仍由请求churn 主导，本身不构成证据；表的界由构造保证。
